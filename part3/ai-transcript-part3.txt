⏺ Fixed. The root cause was a single line in the smooth-scroll handler at the
  bottom of breezy-fulltime-test.html:

  const target = document.querySelector(a.href);

  The href property of an anchor returns the fully resolved URL
  (https://gabrielzurc10.github.io/breezy#features), not the literal #features
  written in the markup. Passing that URL to querySelector throws a SyntaxError
  because it isn't a valid CSS selector — but the crash happens one line after
  e.preventDefault() has already cancelled the browser's native anchor jump. Net
  effect: every # link did nothing on desktop, and on mobile the inline
  closeMobile() handler still ran (menu closed) while the scroll never happened.

  What I changed (in both identical copies, breezy/breezy-fulltime-test.html and
  breezy/part1/breezy-fulltime-test.html):

  1. Use the raw attribute instead of the resolved URL — a.getAttribute('href')
  yields #features, which is a valid selector. I also only call preventDefault()
  once a matching target is confirmed, so a hash with no matching section falls
  back to native behavior instead of silently dying.
  2. Guarded the placeholder links — the many href="#" links (Promotions,
  Careers, etc.) would also have crashed querySelector('#'); they now just
  prevent the page-jump-to-top and return.
  3. Added scroll-margin-top: 140px to sections — the site has a fixed
  three-tier header (36 + 56 + 48 px), so without this, every scroll target
  would land with its top ~140px hidden underneath the header. This makes the
  scroll actually land where the section visibly begins.

  All nav paths now work: main nav, the More dropdown (FAQ), the "Book Air"
  button (#signup), footer links, and the mobile menu — which closes via its
  onclick and then smooth-scrolls to the section.

  now a horizontal timeline, and I verified both layouts with headless-Chrome
  screenshots.

  What changed (CSS only, original class names kept, no HTML edits):

  .step-num circle sits at the top with the title and description below it. The
  two connector lines are ::after pseudo-elements on .step:not(:last-child),
  positioned from calc(50% + 38px) with width calc(100% - 76px) — that's the

  the circles without touching them.

  transition) and the step title transitions to sky blue.

  two-column grid (56px 1fr) — circle down the left, title and description
  stacked to its right — and the connector rotates into a vertical 2px line
  under each circle, again with 10px gaps above and below so it doesn't touch
  either circle.
  - The small script: one line that adds tabindex="0" to each step, paired with
  :focus-visible rules in the CSS so keyboard users get the same grow/color
  effect as hover.

  Two verification notes: the desktop screenshot confirmed circles, gapped
  connectors, and text placement; the mobile capture initially looked like text

  a ~500px minimum window width (the layout ran at 500px while the image

  file, so it's a screenshot artifact, not a layout bug. Re-capturing at 500px

⏺ Done and verified. The steps now fade in one after another when the timeline
  scrolls into view, and the effect degrades cleanly without JavaScript.

  How it works:

  - CSS — a new .steps.reveal .step rule sets the hidden starting state
  (opacity: 0, translateY(18px)) with a 0.5s transition; steps 2 and 3 get
  transition-delay of 0.18s and 0.36s for the stagger. Adding .in to a step
  animates it to visible. A prefers-reduced-motion override skips the animation
  entirely for users who've requested reduced motion.
  - Script — an IntersectionObserver watches the .steps container with
  threshold: 0.5, so the animation fires once half the row of circles is on
  screen. When it fires, all three steps get the .in class (the CSS delays
  produce the one-after-another effect) and the observer calls disconnect(), so
  it plays exactly once and never re-triggers on scroll-back.
  - No-JS fallback — the hiding class .reveal exists nowhere in the markup; it's
  only added by the script (which also bails out if IntersectionObserver is
  unsupported). With JavaScript off, no element is ever hidden, so the section
  renders fully visible.

  Verification via headless Chrome: after load the DOM shows class="steps 
  reveal" and three class="step in" elements; a screenshot happened to catch the
  animation mid-flight — steps 1 and 2 settled while step 3 was still faded and
  offset, confirming the stagger. A script-stripped copy (simulating JS off,
  since Chrome refuses to screenshot with scriptEnabled=false) renders all three
  steps fully visible.

  REST API, no auth. Each post maps to one FAQ: title → question, content →
  answer.
  - HTML stripping uses DOMParser + textContent, which both drops tags and
  decodes entities without executing anything — your post title's &nbsp; comes
  through as a real space and the <p class="wp-block-paragraph"> wrapper
  disappears.
  - Filtering removes any post whose title matches "hello world"
  (case-insensitive), plus anything left with an empty question or answer after
  stripping.
  - Fallback — the accordion's state is initialized from the bundled about.json,
  and the fetched items only replace it when the request succeeds and yields at
  least one usable FAQ. Any failure (network down, non-OK status, bad JSON)
  lands in a silent catch and the bundled content just stays. An AbortController
  cancels the request if the page unmounts mid-fetch.

  Verification against the running build: with the API reachable, the page
  renders exactly one FAQ — "This is a wordpress post" with the plain-text
  answer "This is a test of a wordpress post." — and Hello World is gone. With
  public-api.wordpress.com remapped to a dead address (simulating an outage),
  the page silently renders all five bundled questions. The accordion behavior
  is unchanged in both cases.

  One note: with only one real post on the site right now, the live page shows a
  single FAQ. As you add posts they'll appear oldest-first, and re-titling them
  as questions will make the accordion read naturally.
